# Security & correctness audit — 2026-09-08

Audit of the published `ego-browser-hermes` adapter (origin/main `dc90f85`), performed on an
isolated worktree branch `fix/skill-runtime-hardening`.

## Baseline (before changes)

- `npm install` — 0 vulnerabilities (`npm audit` clean)
- `npm run verify` — typecheck ✓, 54/54 tests ✓, build ✓, MCP JSON-RPC smoke ✓ (12 tools)

## Confirmed defects and fixes

### 1. `navigate` accepted non-http(s) URL schemes (security)

`navigate`'s `z.string().url()` accepted `file:///C:/...`, `javascript:alert(1)`, `data:...`,
and `chrome://...` (verified via zod). A safe tool could open local files or dangerous schemes.

**Fix** (`mcp-server/src/tools/navigation.ts`): added an `isHttpUrl` guard before launch that
rejects anything except `http:`/`https:`. Regression tests assert rejection without spawning.

### 2. Failed calls poisoned the active task-space pointer (state corruption)

`navigate` called `tracker.selected(args.space)` **before** running the script; the shared
`activeSpace()` helper did the same for every other tool (snapshot/page_info/click/fill/wait/
screenshot/upload/download/advanced). When the call failed at the runner level (or, after fix
#3, resolved to a script-level `ok:false`), the active-space pointer was still moved to the
failed space, silently redirecting every subsequent space-less call (reproduced with a mock
runner: a failed call on `poison` caused the next `page_info` to target `poison`).

**Fix**: space promotion is now commit-on-success everywhere.
- `navigation.ts` promotes a requested space to active only after a successful navigation.
- `shared.ts`'s `activeSpace()` no longer mutates the tracker; a new `prepareSpace()` returns
  the target space plus a `commitSpace` callback that `runTool` invokes **only after** a
  successful run (not on runner error, not on `ok:false`). All tools route through this.
- Regression tests assert a failed navigation and a failed (and `ok:false`) snapshot on one
  space leave the previously active space untouched.

### 3. Script-level `ok:false` was swallowed as a success (error semantics)

Tools routed through `runTool` only mapped runner-level `ok:false` to an MCP `isError`. A
script that deliberately resolved `{ ok: false, reason: ... }` (e.g. an empty snapshot after
retries) came back as a normal success — the empty result was invisible to callers.

**Fix** (`mcp-server/src/tools/shared.ts`): `runTool` now promotes any object result whose
`ok === false` to an MCP error, using `error`/`reason` for the message. Regression test asserts
an empty snapshot surfaces as `isError`.

## Verification after fixes

- `npm run verify` — typecheck ✓, **60/60 tests** ✓ (54 existing + 6 new regression), build ✓, MCP smoke ✓
- New tests: `mcp-server/tests/regression.test.ts` (6 tests)

## Out of scope / noted

- Raw JS, CDP, arbitrary CLI, and HTTP remain behind `EGO_BROWSER_ENABLE_ADVANCED=true`
  (unchanged; deliberate opt-in surface).
- Downloads that fail at `saveAs` currently resolve `path: null` with `ok: true`; left as a
  follow-up because `saveAs` failure semantics in the vendored runtime are not yet pinned by a test.
